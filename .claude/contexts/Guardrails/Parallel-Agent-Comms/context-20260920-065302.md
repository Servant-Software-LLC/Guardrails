**The four hazards verified in agentcomm's own source** (these are the load-bearing findings, and
they are what make the issue worth more than a link):

1. **The default bus is the user's git remote.** `src/backends/autodetect.ts`: in a repo with a
   reachable `origin`, the bus resolves to `git+<origin>` and every message becomes a commit pushed
   to a branch on that remote. A task agent running `agentcomm send` would publish outward.
2. **Bus commands write into the working tree.** `src/cli.ts:283` → `autoProvisionHooks()` runs on
   *connect* and writes harness wiring (`.claude/skills/agentcomm/…`) into cwd whenever it is
   missing or stale. Inside a task worktree that write lands outside `writeScope` and fails the
   write-scope check. `AGENTCOMM_NO_AUTO_HOOKS=1` is mandatory; `agentcomm init` (writes
   `CLAUDE.md`) must never run.
3. **Its agent contract is an injection surface.** The generated `CLAUDE.md` text tells agents
   "instructions may be waiting" in the inbox and nudges them to help a "blocked" peer without
   asking the user — directly against "the task prompt is the only spec".
4. **The stop guard costs a turn.** `hookStopGuard` blocks the first stop while mail is unread.
   Bounded (short-circuits on `stop_hook_active`, throttled to once per 45 s) but it spends a turn
   against `--max-turns`.

Plus: Node ≥ 18 CLI (v0.21.1, MIT, 3 contributors, 16 stars, created 2026-06-30) against a .NET
tool, and the `openai-compat` runner (local inference, #570) has no Bash tool, so a CLI-based bus
cannot reach it at all — only a harness-mediated channel would work across runners.
