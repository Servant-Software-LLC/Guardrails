CONTEXT:
The maintainer surfaced a new class of AI model from TypeSafe — "System One," flagship model
"Jev" (docs at https://docs.typesafe.ai/concepts/system-one) — and asked whether it could be
used to replace some of the harness's LLM "judgment calls" with hard, calibrated, typed decisions
instead of free-text prose. The underlying hunch: a recurring pattern in Guardrails work is
compensating for a harness bug by reinforcing skill prose, when the real fix belongs in a
deterministic gate — and a typed-decision model might expose that distinction cleanly, or might
remove some of the drift at the source.

This session researched System One/Jev from the docs, surveyed the harness's existing model-driven
decision points, and filed a GitHub research issue capturing the hypothesis, the candidate
decision points, the hard limits, and a research plan. The maintainer then raised a follow-up:
Jev looks lightweight, so open-weight System One-style models may arrive soon, which would remove
the biggest objection (hosted-only, data egress) and should shape how the research is scoped.

- Filed GitHub issue #755: "Research: could a calibrated typed-decision model (TypeSafe System
  One / Jev) make the harness's judgment calls, instead of reinforcing skills against drift?"
  — https://github.com/Servant-Software-LLC/Guardrails/issues/755
  Body covers: what Jev is, a decision-point table (criticality assessment, unknown-failure

  difficulty routing #201/#533) mapped to Jev's primitives, five hard limits (can't stop an

  work, Jev can't help" / "harness bug patched in prose" buckets; replay criticality decisions
  head-to-head against recorded GREEN/RED outcomes, measuring wrong-proceeds/calibration/latency;
  check the 32k state budget per decision point), and a Charter-reviewed findings-doc deliverable
  with go/no-go per decision point. Explicitly out of scope: wiring Jev into any production or
  certification path.
- Posted a follow-up comment on #755 (https://github.com/Servant-Software-LLC/Guardrails/issues/755#issuecomment-5743996455)
  and folded its point into the issue body, addressing the maintainer's open-weight-models remark:
  - Build the durable research artifacts (state assemblers, question decomposition, the replay
    comparison against GREEN/RED) **provider-agnostic** — one interface (questions in,
    `{option→probability}` out) so Jev today and an open-weight model later are the same
    experiment.
  - Calibration, not the typed-answer format, is the part an open-weight clone might not
    reproduce (typed/constrained output is easy to copy; calibration requires training against
    outcomes) — so the comparison must report calibration separately per candidate.
  - Added a third comparison candidate available *today*: a local model with output constrained
    to a fixed label set (grammar/JSON-schema constrained decoding via llama.cpp/vLLM/MLX),
    normalized into a probability distribution, then calibrated post-hoc (Platt scaling / isotonic
    regression) against our own recorded outcomes. If this comes close to Jev, no need to wait for
    an open-weight release; if it falls well short, the gap quantifies what a real open-weight
    System One model would add. This ties directly into the local-inference roadmap
    ([[local-inference-telemetry-roadmap]] memory — GH #570, Mac Studio Ultra end of Oct 2026).
