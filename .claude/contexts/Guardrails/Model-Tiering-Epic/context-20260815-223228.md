--- The macOS saga (#450) — RESOLVED, worth keeping for the lesson ---
- `cb39c5c` made `WorktreeSweepBookkeeping` compare a git-reported path against a harness-derived one
  through a new `RealPath` walk. It was **green on Windows and RED on macOS CI** — the fix's own tests
  failed on the OS the fix was for, twice.
- **Root cause, confirmed by three MacBook probes that eliminated suspects in order:** (1)
  `ResolveLinkTarget` is leaf-only and *throws* on a missing path; (2) `/var` **does** resolve — killing
  the API-blind-spot theory; (3) the walk works end-to-end in isolation. That left exactly one shape: **a
  link whose target is absolute but written in the ALIASED spelling.** The walk adopted such a target
  verbatim and threw away the canonicalisation it had already accumulated. macOS supplies the outer link
  for free — `LinkedTree` builds under `Path.GetTempPath()`, i.e. `/var` → `/private/var`.
- **Fixed in `a05e3b8`**: re-canonicalises every adopted target from its root, bounded by
  `MaxLinkDepth = 40`, degrading to the literal rather than throwing (a runaway is real and NOT circular
  per-link — `/x/a → /y/a` with `/y → /x` — so the runtime's SYMLOOP detection never fires).
- **The bug is UNREACHABLE through the Windows filesystem, and that was PROVEN, not assumed**: Windows
  resolves via `GetFinalPathNameByHandle`, which canonicalises the whole path, so `returnFinalTarget:true`
  always hands back an already-canonical target. Hence the internal seam
  `RealPath.ResolveWith(path, resolveSegment)` with an injected resolver, and two tests proven **by
  mutation on Windows**: adopting verbatim → `Expected: C:\real\inner, Actual: C:\alias\inner`; removing
  the depth guard → **stack overflow, exit `0xC00000FD`**.
- Also discovered: `Directory.CreateSymbolicLink` fails unprivileged on the dev box, so `LinkedTree` has
  been silently using its `mklink /J` junction fallback all along.
- **The caveat is now RETIRED.** The harness developer had flagged that a green `RealPathTests` proves
  only the walk, and that `WorktreeSweepBookkeepingTests` was the assertion that had to go green. The
  release run exercised the full suite on real macOS — so that is confirmed, not inferred. No MacBook
  verification step remains.
