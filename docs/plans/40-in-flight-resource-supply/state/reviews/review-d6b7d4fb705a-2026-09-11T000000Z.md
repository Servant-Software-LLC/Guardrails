## Addendum — 2026-09-11, from plan 39's review

Reviewing `39-incremental-delivery` surfaced a defect in an idiom these three documentation
guardrails share, so they were amended and this plan re-stamped at a new hash
(`cf6c98c96355` -> `d6b7d4fb705a`). The marker self-staled correctly when the bodies changed —
the #260 guarantee working as intended.

**The defect, measured on plan 39.** A lazy `(?s)<!--.*?-->` treats a PROSE MENTION of `<!--` as
a comment opener and runs to the next real `-->` anywhere later. On
`.claude/skills/plan-breakdown/SKILL.md` that removed **169,334 bytes — 44.8% of the file — in
one 167,393-byte span**, because line 636 is the skill's own sentence teaching this idiom. The
unterminated-`<!--` precondition reported HEALTHY throughout, because a `-->` does exist later.

**Not live on this plan's subjects, and that was measured rather than assumed**: the strip
removes 2,615 / 0 / 95 bytes from the SSOT, the README and the domain-knowledge skill, biggest
single span 2,037 — all legitimate balanced comments. The amendment is preventive here and
curative there.

**The fix**, applied to all three: mask `<!--`/`-->` inside fenced blocks and inline code spans,
strip, then UNMASK. Inside a fence or a code span, `<!--` is literal text a reader SEES —
Markdown renders it — so it cannot be an opener; and unmasking preserves fence content, which
keeps the counter-rule (a token in a usage fence legitimately satisfies a clause). The
belt-and-braces precondition now runs on the MASKED text, so an opener with no closer really is
unterminated.

**Re-verified after the amendment:** all three exit 1 with every clause firing (6, 5, 4); the
HTML-comment mutant still fails to game them; rendering prose still passes.
