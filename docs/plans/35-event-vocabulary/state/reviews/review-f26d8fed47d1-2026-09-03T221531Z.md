## B7 — BLOCKER: task 13 was UNSATISFIABLE as written

**The defect is mine, in the plan, not in the agent's work.** Three attempts and an overwatch
intervention were spent on a task that could not be completed within the constraint the plan imposed.

| | |
|---|---|
| Task 12's test | *"attach a live subscriber, append a row, then immediately shut the server down, and assert the subscriber **received** that row"* |
| Task 13's prompt | *"`_listener.Stop()` runs first in `DisposeAsync` and can abort an in-flight response … **Do not attempt to close that gap here**"* |

The test **requires** the row to survive listener teardown; the implementing task is **forbidden** the
only change that lets it. That is the #470 required-vs-forbidden collision **lifted from the clause
level to the plan level** — two individually reasonable statements, in different files, that no
implementation can satisfy together. Neither `validate`, nor `graph --check`, nor the pre-run review's
Probe C (which reconciles clauses *within a guardrail file*) has a reading that spans two tasks.

### What the run established, empirically, that the design had asserted wrongly

The agent tried ~10 variants and reported:

1. Without extra synchronization the final write throws
   `System.ObjectDisposedException: … 'System.Net.HttpRequestQueueV2Handle'` — **and that exception was
   being swallowed by `WriteEventsStream`'s existing catch-all**, which is why the defect presents as
   *"the row was silently dropped"* rather than *"shutdown threw"*. A pre-existing silent failure in
   shipped code, found by accident.
2. It then built the strongest in-scope mitigation available — a `CancellationTokenRegistration` that
   BLOCKS `_shutdown.Cancel()` until the tail loop's final read, write and an explicit
   `HttpListenerResponse.Close(byte[], willBlock: true)` have all completed with zero exceptions,
   confirmed by diagnostic logging. **Provably complete before `Stop()`/`Close()` ran — and the client's
   next read still returned null.**
3. Conclusion: `_listener.Close()`'s underlying `HttpCloseRequestQueueHandle` cancels outstanding I/O
   for the **whole request queue at the kernel level**, independent of managed-layer completion. No
   in-process synchronization confined to `WriteEventsStream` can work around it.

**So §3.8 as designed was not "best-effort" — it was 0% effective.** A mechanism that never delivers is
not a weaker guarantee; it is dead code. The plan's §9.3 presented that as a considered trade
(*"guaranteeing delivery would mean the run waiting on its own HTTP clients"*), and the trade rested on
a premise nobody had executed.

### The fix, which is smaller than the design assumed

`DisposeAsync` **already contains** `await Task.WhenAll(pending)`, whose own comment reads *"Wait for
every dispatched request (including a still-polling GET /events stream) to notice `_shutdown` and return
**before disposing it out from under them**."* It runs three lines **after** `_listener.Stop()` has
disposed the handle. **That comment is false in shipped code today, independent of this plan.**

Moving the drain above `Stop()`, with a bounded timeout, closes the gap for the ordinary shutdown path.
The original worry does not apply to it: the handlers have already been signalled by `_shutdown`, and
this stream's poll interval is 150 ms, so the wait is on the server's own loop — not on a client.

### Why the pre-run review missed it

Every probe that could have caught it is scoped to one artifact. Probe C reconciles required-vs-forbidden
**within a guardrail file**; the #474 reachability probe traces a **datum** to its carrier; §4 checks
that some task's `writeScope` **covers a path** — and task 13's scope did cover `LogServer.cs`. None of
them asks the cross-task question this needed: *does the change task N is forbidden from making happen to
be the one task M's test requires?* Worth a probe of its own.

### The pattern, for the third time in one session

This is the same shape as the plan's own §3.8 "three lines" claim and as B2's grep: **a structural claim
about the codebase, asserted in a prompt, never executed.** #578 covers counts, routing, exclusivity and
locations. It should cover **size and feasibility** claims too — *"the change is three lines"* and
*"closing that gap would mean X"* are exactly as checkable and exactly as load-bearing, and here one of
them cost three attempts and an overwatch intervention.

## Second correction, after run 2

Run 2's attempts died alternately on **both** ceilings — attempt 5 `Timeout` (1800s), attempt 6 `MaxTurns` (100). The overwatcher can raise turns at run time but **cannot raise the persisted wall clock**, so every further attempt was capped at 30 minutes regardless. Run 2 was stopped deliberately rather than spending another attempt against a wall.

Ceilings raised to `maxTurns: 250`, `timeoutSeconds: 5400`. **Nothing about the deliverable is large** — it is a line move in `DisposeAsync` plus a final read. What is large is the VERIFICATION loop: a race-condition fix whose guardrails run two filtered integration suites per pass. The breakdown's `maxTurns` archetypes model deliverable difficulty and research overhead; they do not model **verification cost**, which is the binding constraint here. That is the same gap #584 proposes to close with a read-volume archetype, and this is a second, sharper instance of it.

Also checked, and NOT the problem: task 12's authored test. It seeds a row so the chunked headers flush, drains it so the tail loop's next read is guaranteed empty, waits past one poll cycle so the loop is provably parked, then appends and disposes immediately behind it. It is deterministic in the way that matters and becomes satisfiable the moment the drain moves. The test is right.
