## The three defects

### 1. A guardrail that could not PARSE (task 11) — filed #473

`02-per-tier-spend-tests-pass.ps1` line 24 wrapped a word in **backticks inside a double-quoted
string**. In PowerShell 7 the backtick is the escape character, so `` `u `` opens a Unicode escape
requiring `` `u{…} ``; `` `un `` is invalid and **pwsh rejects the whole file at parse time**. Nothing
in the script ever ran — the attempt log holds only the `ParserError`, with no restore, no build and
no `dotnet test` output. It failed identically whether the implementation was right, wrong or absent,
and cost 2 attempts plus a discarded verified implementation.

**Review gap:** the #302 probe names a `pwsh` parse as the cheap FIRST pass. I parse-checked the
seven scripts I authored and never swept the eleven **machine-authored** ones recovered from the
quarantine — where an unexecuted script was most likely to hide. Sweeping all 107 takes ~3 seconds.
**FIXED**; sweep now clean (the only remaining hit is an inert copy under `logs/…/rejected/`).

### 2. A writeScope that cannot reach its deliverable (task 13) — filed #474

Its guardrail required `AttemptJournaler.cs` to journal `Usage`. But the journaler builds
`AttemptRecord` from an **`ActionRun`**, and `ActionRun` carries `CostUsd` with no usage sibling
(`ActionRunner.cs:352`) — a file owned by task 07 and already merged. The agent's only in-scope moves
were to halt or to satisfy the guardrail with a token that journals nothing. It halted, correctly.

**Authoring gap, mine:** I traced `PromptResult → AttemptRecord.Usage` on type names without checking
what the journaler actually reads. The parallel `CostUsd` path sat in the same files.

**RESOLVED** by narrowing task 13 to the two hops its scope can deliver (parse + carry), replacing
`01-all-three-hops-landed.ps1` with `01-both-hops-landed.ps1`, and adding a negative clause so an
agent that goes hunting for the severed hop is caught rather than rewarded. The journalling hop is
deferred and filed as **#475** so the unpopulated field is visible rather than silently half-done.

### 3. A terminal-gate requirement with NO owning task (found during remediation)

The plan's terminal gate asserts `docs/plans/02-schemas-and-contracts.md` mentions `tierSource`. The
SSOT had **zero** occurrences and **no wave-2 task owned the file**. The gate fires after all 13
tasks, where there is no retry and delivery is withheld — the most expensive possible instance of the
#474 class.

The evidence was in the folder the whole time: task 04's guardrail comment reads *"the SSOT task
(14) — which documents the answer in the new 9.6"* and *"the three fields task 14 consumes"*, and its
prompt says *"publish it to state so the SSOT task (14) can document it"*. The wave brief likewise
states *"Some task in this wave must own `docs/plans/02-schemas-and-contracts.md` in its
`writeScope`."*

**So the truncated breakdown planned FOURTEEN tasks, not thirteen.** It was cut mid-task-12; I
recovered 11, hand-authored 12 and 13 from the wave gates' references, and never noticed 14 was also
owed. **The review's §4 missing-insertion check is exactly the probe for this** — *"any guardrail
referencing an artifact no ancestor produces → a missing guardrail-enabling task"* — and I did not
run it against the terminal gate.

**RESOLVED** by authoring `14-land-ssot-schema-deltas` (tier 7; `dependsOn` 04/09/11/13; single-file
`writeScope`). It consumes task 04's already-published §6.3 answer from state rather than re-deriving
it.
