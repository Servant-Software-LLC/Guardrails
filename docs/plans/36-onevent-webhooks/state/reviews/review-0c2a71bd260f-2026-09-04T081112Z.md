## A fix that would have killed the run

The `GR_SUBJECT` finding was correct; **the fix this review first specified was not**, and it is worth
recording because it would have failed loudly and expensively.

`GR_SUBJECT` is not an ad-hoc name — it is the harness's own protocol constant
(`src/Guardrails.Core/Samples/SampleVerifier.cs:76`), and `SampleVerifier` binds each sample half **both**
as the first positional argument and in that variable (`:332`/`:336`), with `:321` warning that *"a verifier
that supplies only one silently mis-verifies half the corpus."* Renaming it to
`GUARDRAILS_SAMPLE_SUBJECT` would have left the guardrail reading the real `RunCommand.cs` for both halves;
the `.valid` half exits 1; and the **pre-DAG sample-verification preflight halts the whole run (exit 2)** —
before a single agent token is spent.

The applied fix reads **`$args[0]`, not the environment**. It is strictly stronger than the rename: a real
run launches `pwsh -File <script>` with the guardrail definition's own args, and this guardrail declares
none, so `$args` is empty **by construction** rather than by the harness remembering to strip a prefix.
Leak probe: `GR_SUBJECT=<valid sample>` with no argument → exit **1** (reads `RunCommand.cs`, as it must).
`guardrails samples verify` → `OK: 1 sample pair(s) verified, 0 findings.`

A second instruction from this review was also corrected by measurement: `ARepeatedOnEventFlagIsRejected`
would have been a **false green**, because System.CommandLine 2.0.9 rejects a repeated single-arity option
itself (`guardrails graph … --format a --format b` → exit **1**, *"expects a single argument but 2 were
provided"*). Declared as the originally-specified `Option<string?>`, that test passes on a tree with zero
`--on-event` validation — and then fails task 08's own census, which task 08 cannot fix because the census
is not in its write scope. `--on-event` is now declared multi-valued (`Option<string[]>`,
`ArgumentArity.OneOrMore`) with task 09 doing the count check.

### Accepted gaps, named rather than silently carried

- **§6.5's fourth validation deliverable** — the warning on plain `http` to a non-loopback host — has no
  witness. Covering it honestly is network-dependent and expensive (a non-loopback endpoint makes the run
  actually attempt delivery, paying the 45 s per-row ceiling until the circuit opens). The cheap route, if
  wanted later, is a Core-level unit test of the warning predicate rather than a CLI integration test.
- **Task 06 has no policy-regression guardrail** although its `writeScope` includes the file task 05
  implemented; task 07 has exactly that. A task 06 that damages `IsRetryable` or `RedactUrl` settles green
  and surfaces at task 07, whose retry feedback blames the wrong agent.
- **Case-sensitivity asymmetry**: tasks 02/04/06's red censuses match case-insensitively while the forward
  censuses use `-cmatch`. A wrong-cased method passes red and fails forward on a task that cannot edit the
  test — it degrades to an honest `needsHuman`, and all three headers now say so.
- **A₂'s deepest residual**: the censused tree is the **plan's** baseline, not each task's. The one non-root
  source clause (task 09's `WebhookEventSink.TryStart(`) was checked against its ancestor's prompt and
  cannot be pre-satisfied; the rest are root tasks.
