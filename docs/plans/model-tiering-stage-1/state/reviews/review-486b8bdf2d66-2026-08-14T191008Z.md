## What happened

Addendum 1 fixed all six affected guardrails. Four of those six belong to tasks that had **already
succeeded** (01, 03, 05, 06). A task's definition hash covers its guardrail bodies (#260), so on the
next `guardrails run` the harness correctly reported definition drift:

```
DEFINITION DRIFT - one or more already-succeeded tasks changed since they last succeeded (SSOT 7.2).
  01-author-tests-runner-kind-and-axes:    sha256:fe998c. -> sha256:877b78.
  03-author-tests-registry-kind-dispatch:  sha256:11dca5. -> sha256:15a243.
  05-author-tests-action-tier:             sha256:fd20d6. -> sha256:9166ff.
  06-implement-action-tier:                sha256:a29c85. -> sha256:3d01f6.
  Re-run set (drifted + descendants): all 9 tasks
```

Accepting would have rewound 6 commits and re-run every task — roughly the $78.90 already spent — to
re-verify work independently confirmable as correct. The drift detector was right; the authoring
mistake was fixing all six at once when only the unblocking subset needed to land mid-run.

## Residual risk, stated plainly

Four guardrails remain defective in this plan folder:

- **Tasks 01, 03, 05** keep a `tests-fail-on-stubs` whose filter any sibling's red tests can satisfy —
  the tautology of A2.
- **Task 06** keeps the over-broad forward filter of A1. Latent only: if 06 ever re-runs after task 03's
  red tests are on its base, it deadlocks exactly as task 02 did.

All four belong to completed tasks, so none will execute again in this plan's remaining run. They
verify nothing going forward; the cost is to the durable record, not to the run's soundness.

**The red proofs those guardrails were meant to establish are independently confirmed**, which is why
this trade was acceptable rather than merely cheap:

- **Task 03** — its four `RegistryKindDispatchTests` were measured **failing** on the plan branch during
  addendum 1 (`Failed: 4, Passed: 39, Total: 43`). Genuinely red, observed directly, with task 04 still
  unrun.
- **Tasks 01 and 05** — task 02 spent four attempts making the 18 `PromptRunnerSchemaTests` pass, and
  task 06 likewise for `ActionTierTests`. Vacuous tests would have passed against the stubs immediately.
  Indirect, but conclusive.

So the tautology weakened the *mechanism* of proof without, in this instance, letting a bad test corpus
through.

## Doctrine note for the next plan

The generalisable lesson, beyond #455: **a guardrail fix for an in-flight plan must be scoped to tasks
that have not yet succeeded.** Fixing a completed task's guardrail buys nothing — it cannot re-verify
what is already journaled — and costs a full re-run of that task and every descendant. The correct
sequencing is to fix what unblocks now, and fold the rest in when the plan is complete and no resume
will follow.
