## Why this addendum exists

The first pass approved the plan. The run then halted at `02-implement-runner-kind-and-axes` with
`needs-human`, and the escalating agent's diagnosis was correct: **a defect the first pass did not
look for.** This addendum records it, fixes it plan-wide, and states why the original method missed it.

The task's own report was accurate on every point — deliverable complete, build clean, write-scope
clean, its own 18 tests green and unmodified — and it correctly refused to take the "just implement
the sibling's task too" option unilaterally. Nothing below is a criticism of the run.

## The defect: a task guardrail keyed on a plan-wide trait

Every Stage 1 test class carries `[Trait("Category", "ModelTieringStage1")]` — load-bearing, because
the baseline preflight uses `Category!=ModelTieringStage1` to exclude the new tests from the
start-from-green check. That part is correct.

The breakdown then reused the *same* trait as the filter for **six task-level guardrails**, which makes
each one assert the state of all 43 Stage 1 tests rather than the ~18 its own task owns. Two distinct
failure modes came out of that, in opposite directions:

**Forward — `01-tests-pass.ps1` in tasks 02, 04, 06.** Requires every Stage 1 test green. Task 03
authors deliberately-red dispatch tests; they are fixed by task 04; task 04 `dependsOn` task 02. So
task 02 could only pass after a task that depends on it had run. A closed cycle across the guardrail
layer, invisible in the DAG — `validate` and `graph --check` both pass, because the cycle is not
between tasks, it is between a task and a *sibling's test corpus*.

**Inverse — `02-tests-fail-on-stubs.ps1` in tasks 01, 03, 05.** Requires a non-zero exit, i.e. *some*
Stage 1 test red. Once any sibling's red tests are on the base, this passes **regardless of whether the
task's own tests fail at all**. Tasks 01, 03 and 05 run concurrently in tier 0; whichever integrates
second gets certified "red" by the first's tests. The TDD-red proof — the strongest anti-tautology
check a breakdown has (#155) — degraded to merge-order luck.

Task 06 passing in the run is not evidence against this: it branched before task 03's red tests reached
its base. Reorder the merges and 06 deadlocks exactly like 02 did.

## Second finding, introduced by the fix: the zero-match hole

Narrowing a `--filter` creates the hole the salvage-advice review found as its F4: a filter matching
nothing **exits 0**. None of the six had a guard. Left unguarded, a renamed class or a dropped trait
would silently vacate the check instead of failing it.

The first pattern written for the guard was wrong, and probing (not reasoning) settled it — the #248
rule, "verify the pattern against real tool output". Observed on this SDK:

| Case | `dotnet test … -v q` output | Exit |
|---|---|---|
| zero match | ends at `A total of 1 test files matched the specified pattern.` — **no diagnostic at all**, not even `No test matches the given testcase filter` | 0 |
| ≥1 match | `Passed!  - Failed: 0, Passed: 11, Skipped: 0, Total: 11, …` | 0 / 1 |

So the discriminator is the **presence of a `Total:` count ≥ 1**, not any error string. A guard keyed on
the error string was written first, executed against the real tool, and observed to **not fire** — which
is precisely the failure the #248 rule exists to prevent, caught before it shipped.

Verified live on `master` (which has no ModelTiering tests, so every filter matches zero):

```
forward (02): EXIT=1  FILTER MATCHED NO TESTS (…~PromptRunnerSchemaTests) - this guardrail verified NOTHING …
inverse (01): EXIT=1  FILTER MATCHED NO TESTS (…~PromptRunnerSchemaTests) - this guardrail verified NOTHING …
```

Both directions now fail loudly. Before this addendum the three **forward** guardrails were also
**vacuous on a base without the tests** — on `master` they exited 0 having run nothing. That is a second,
quieter hole the same guard closes.

## Why the first pass missed all of this

Stated plainly, because the method has to change, not just the files:

1. **The six `dotnet test` guardrails were never examined.** The first pass swept the *content*
   guardrails for tautologies and smoke-tested the *script* guardrails two-sided. The test-running
   guardrails were scoped out as slow and environment-dependent, so their filters were never read.
2. **Both probes test a guardrail in isolation.** This defect is only visible by cross-referencing a
   filter's *scope* against the DAG's *dependency edges* — asking "can the task that owns this
   guardrail fix everything its filter selects?" No single-guardrail probe can see it.

The guardrails-review catalogue already carries the rule that would have caught it — *"Over-broad:
'all tests pass' anywhere except the terminal `<plan>/guardrails/` folder"*. A task-level `tests-pass`
keyed on a plan-wide trait is that anti-pattern wearing a filter. The rule existed; the pass did not
apply it. Filed as a `/plan-breakdown` + `/guardrails-review` doctrine gap, since the breakdown
generated all six this way and the review approved them.
